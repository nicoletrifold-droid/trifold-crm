`landing-pages/*` hospeda sites estáticos publicados como **projetos Vercel independentes**, não como parte do `trifold-crm`. Deploy é feito direto do diretório local com `vercel deploy --prod --yes --scope trifold-s-projects` executado de dentro da pasta — sem commit, sem build step, sem quality gate do CRM.

Projetos criados até agora:
- `trifold-design-system` (`prj_1SRBOXwTclTFwGDz3zjIO6uM0pMG`) → https://trifold-design-system.vercel.app — export do Claude Design canvas, HTML puro + `support.js`, ~121MB de imagens, 214 arquivos. Primeiro deploy em 2026-08-17.

**Why:** o usuário quer link compartilhável rápido para material de marketing/design; misturar com o projeto Vercel de produção do CRM (`prj_s3ARh1fpDnzbx9ua4MYJf9iqdRhj`, rootDirectory `packages/web` — ver [[vercel-project-setup]]) quebraria o build da aplicação.

**How to apply:** ao receber pedido de publicar site em `landing-pages/`, deploy direto da subpasta (ela tem seu próprio `.vercel/project.json`, o do repo raiz continua apontando pro CRM). Redeploy = repetir o mesmo comando de dentro da pasta. Deploy **não** depende de commit — publique primeiro, versione depois se o usuário pedir.

**Histórico (branch antiga, superada pelo #501):** `feat/landing-pages-trifold-design-system` chegou a ter os 269 arquivos / ~85MB (commits `b82edbb9` vind + `f1ec5431` design-system). Detalhes que importam num commit futuro: Detalhes que importam num commit futuro:
- Cada subpasta tem `.gitignore` local com `.vercel` — os IDs de projeto Vercel nunca entram no git. Não precisa excluir manualmente.
- `uploads/` (57MB) e `brand_imgs/` são os originais em resolução cheia do export do canvas e **não são referenciados por nenhum HTML/JS** (só `assets/`, 20MB, tem as 62 referências vivas). Foram commitados de propósito, como fonte para re-exports.
- `api/contact.js` lê `process.env.RESEND_API_KEY` — nada hardcoded; o scan de segredos em `landing-pages/` passou limpo. **Com esse arquivo o `trifold-design-system` deixou de ser 100% estático:** a pasta `api/` é detectada zero-config pela Vercel e vira Serverless Function Node, sem nenhuma entrada no `vercel.json`. Ou seja, o projeto tem runtime — env vars e logs importam. Ver [[verify-email-delivery-not-http-200]].
- Commitar aqui é seguro para o build do CRM: `rootDirectory` do projeto Vercel `trifold-crm` é `packages/web` (verificado via API em 2026-08-20), então `landing-pages/` na raiz fica fora do build root. **Mas "fora do rootDirectory" ≠ "não dispara deploy":** o projeto `trifold-crm` tem `productionBranch = main` e `commandForIgnoringBuildStep = None` (verificado via `GET /v9/projects/{id}` em 2026-08-20), ou seja **qualquer** push em `main` dispara build+deploy de produção do CRM, mesmo que o diff não toque em um único arquivo de `packages/web`. Então mergear PR de `landing-pages/` = redeploy de produção do CRM de graça. Avisar sempre; preferir agrupar com um deploy que já tenha motivo próprio. Se isso incomodar de forma recorrente, o fix é configurar Ignored Build Step no projeto Vercel.

**Como sincronizar a branch com o disco (padrão validado 2026-08-24):** `landing-pages/` continua **untracked na working tree principal** (o repo raiz fica em `main`/branch de outra epic, com dezenas de arquivos não relacionados pendentes). Para atualizar a branch sem contaminar nada: `git worktree add <scratchpad>/wt-landing feat/landing-pages-trifold-design-system` → `rsync -a --delete --exclude .vercel --exclude .git` da pasta local para dentro do worktree → `git status` no worktree revela exatamente o delta → commit + `git push origin feat/landing-pages-...` (push normal, branch já existe) → `git worktree remove --force`. O PR #471 atualiza sozinho. Antes do commit, rodar o scan de segredos ([[no-add-all-secret-leak]]) na pasta inteira, não só nos arquivos alterados.

**O delta costuma ser bem menor que o descrito no pedido:** em 2026-08-24 o pedido listava ~9 features (CSP, blog por slug, View Transitions, hardening do form...) mas o `rsync` revelou que tudo isso já estava em `f1ec5431` — o delta real eram 3 arquivos (percentuais de obra + CTA do slide 3). Isso acontece porque o site é deployado direto na Vercel sem passar por git, então o usuário lembra do trabalho mas não de quando ele foi versionado. Nunca inferir o escopo pelo prompt: o `git status` do worktree é a única fonte de verdade. Ver [[vercel-static-deploy-concurrency]].

**Padrão de entrypoint (exports do Claude Design canvas):** o canvas não gera `index.html`; a página inicial vem como `Home.dc.html`. Não criar `index.html` com meta-refresh — causa flash de redirect visível. Usar `vercel.json` com `{"rewrites":[{"source":"/","destination":"/Home.dc.html"}]}`: `/` responde 200 direto (header `content-disposition: inline; filename="Home.dc.html"` confirma o rewrite), sem 3xx.

**`.dc.html` é template client-side, não HTML final:** o arquivo servido contém placeholders `{{ s.ctaHref }}`, `{{ s.logoSrc }}` etc., resolvidos em runtime por `support.js`. Consequências ao validar deploy: (1) `curl` + grep só prova que o *template* e o array de dados (ex. `rawSlides`) subiram — para provar que um `href` resolve pro valor certo é preciso renderizar de verdade (Chrome headless via playwright do pnpm — o `NODE_PATH` correto é `playwright@1.60.0`, **não** `@playwright+test@1.60.0`; receita completa em [[headless-render-validation]]); (2) o browser dispara requests pelos `src="{{ ... }}"` literais antes da hidratação, gerando **404s benignos e pré-existentes** em `/%7B%7B%20c.src%20%7D%7D` e `/%7B%7B%20s.logoSrc%20%7D%7D` — não é regressão, não investigar. Ver [[vercel-static-deploy-concurrency]] para o resto do protocolo de validação.

**Validar um slide específico do carrossel hero da Home (headless):** o carrossel tem **autoplay curto** — clicar na seta e esperar 2-4s antes do screenshot deixa o slide errado ativo (falso negativo). Protocolo que funciona: clicar `button[aria-label="Próximo slide"]` em loop, checando a cada iteração `getComputedStyle(parentElement).opacity` da `div` cujo `background-image` casa com o banner alvo, e tirar o screenshot **imediatamente** quando opacity ≈ 1. Os valores de `background-position` resolvidos (ex. `66% 50%` no mobile vs `50% 50%` no desktop) são legíveis via `getComputedStyle` e servem como prova numérica além do screenshot. As bolinhas (dots) não são selecionáveis por heurística de `border-radius:50%` — use o `aria-label` das setas.

**Guards de segurança (deploy 2026-08-19) — como validar sem falso negativo:** `vercel.json` ganhou bloco `headers` para `/(.*)` (X-Frame-Options DENY, nosniff, Referrer-Policy, Permissions-Policy, CSP) e `api/contact.js` ganhou honeypot (`empresa`), guarda de tempo (`loadedAt`, mín. 2s), checagem de Origin/Referer e rate limit em memória. Consequências para validação futura:
- **`curl -X POST /api/contact` sem header `Origin` retorna 403 `forbidden_origin` de propósito** — não é regressão. Para testar de verdade: `-H "Origin: https://trifold-design-system.vercel.app"` (allowlist também tem `trifold.eng.br` e `www.`). Com Origin válido + `"loadedAt":1`, o esperado é **502 `email_send_failed`** (sandbox do Resend, pré-existente). Com `"empresa":"spam"` o esperado é **200 `{"ok":true}`** (honeypot responde sucesso falso, não chama o Resend).
- Ordem dos checks em `contact.js`: rate limit → origin → honeypot → guarda de tempo. Logo o **rate limit (5 req / 60s por instância warm) conta até as requisições que tomam 403** — não dispare mais de ~4 testes seguidos ou você recebe 429 e interpreta como falha.
- A **CSP mantém `'unsafe-inline'` + `'unsafe-eval'` em `script-src` e `'unsafe-inline'` em `style-src` de propósito**: o runtime `support.js` avalia o `<script type="text/x-dc">` dinamicamente (Babel em runtime) e o site depende de milhares de `style="..."` inline. Endurecer esses dois pontos quebra menu/carrossel/formulário. `script-src` também precisa de `https://unpkg.com` por causa do `@babel/standalone` lazy. Não "corrigir" isso como achado de segurança.

**CDNs externos no `support.js`:** o runtime carrega 3 libs por URL+SRI. React e ReactDOM 18.3.1 foram auto-hospedados em `assets/vendor/` (2026-08-17, ganho de LCP — mesmos bytes do unpkg, SRI hardcoded continua batendo). **`@babel/standalone@7.29.0` permanece em unpkg.com** e é carregado *lazy* via `ensureBabel()`, fora do caminho crítico. Portanto "grep unpkg.com no support.js servido = vazio" é critério de validação INCORRETO: valide só `REACT_URL`/`REACT_DOM_URL`. Auto-hospedar Babel é um follow-up possível (é a última origem de terceiro restante).
